# 开源笔记复用与精简排期

日期：2026-10-25；修订 r2。依据用户反馈：笔记部分优先复用成熟开源实现，缩短首个可用版本周期。

## 1. 修正后的交付基线

当前优先交付用户可日常使用的 Windows 版本：B站、本地视频、PDF、Markdown 知识库、带来源的 AI 问答、保存和继续修改笔记。

笔记编辑、渲染、工具栏、目录树和文件监听采用现成组件。应用开发集中在宿主集成、课程证据、本地文件服务和 AI 工具调用。

此前 8–11 周按完整 Beta 的范围估算，其中包含完整 ASR/OCR、数据库重构、反向链接、发行升级和长时间稳定性。这个数字不作为首个可用版本的排期。减少笔记开发只能节省其中一部分；其余压缩来自沿用观察核心、渐进存储和调整阶段边界。

## 2. 直接集成的组件

| 能力 | 组件与官方来源 | 授权核对 | 首版接入方式 |
| --- | --- | --- | --- |
| Markdown 编辑、工具栏、预览 | [@uiw/react-md-editor](https://github.com/uiwjs/react-md-editor) | MIT | 直接封装 React 组件，受控 Markdown 字符串连接读取/保存接口，按官方示例接公式插件 |
| 文件夹树、选择、重命名交互 | [react-arborist](https://github.com/jameskerr/react-arborist) | MIT | 使用受控数据和回调；真实文件改名/移动由 VaultService 完成，组件内部状态变化不等于磁盘已写入 |
| 文件新增、修改、删除监听 | [chokidar](https://github.com/paulmillr/chokidar) | MIT | 主进程/文件服务监听授权目录，去抖并过滤应用备份、.obsidian等目录，不追随未授权符号链接 |
| 小规模笔记搜索 | [Fuse.js](https://github.com/krisk/Fuse) | Apache-2.0 | 复用文件名/文本模糊搜索；中文精确子串补充匹配，后台增量更新，限定读取数量和大小 |
| PDF 阅读 | [PDF.js](https://github.com/mozilla/pdf.js) | 沿用原调研 | 直接集成阅读与页面定位，扫描页OCR不作为首版门槛 |

调研时只检查官方资料与实际LICENSE；后续0.1.0-core开发已安装锁定版本，并接通uiw、react-arborist、chokidar和Fuse的基础流程，具体实测见 [开发日志](开发日志.md)。调研提交快照不等于安装版本，实际版本以package-lock.json为准。Vditor、MDXEditor和Milkdown仍只做资料比较。

备选编辑器：

- [Vditor](https://github.com/Vanessa219/vditor)：MIT，提供所见即所得、即时渲染和分屏模式。如果后续更重视 Typora 式体验，可替换编辑器适配层；需验证 Markdown 保存保真，并把默认 CDN 资源改为本地打包。
- [MDXEditor](https://github.com/mdx-editor/editor)、[Milkdown](https://github.com/Milkdown/milkdown)：均核对到 MIT，可用于后续富文本体验评估；当前先避免让富文本模型转换成为已有笔记接入的前置工作。

选择 uiw 的原因是与现定 React 栈直接匹配、以 Markdown 字符串连接本地文件，适合快速形成可读写的工作流。这是本方案的选择判断，不代表本轮已完成编辑器性能或保真对比测试。

## 3. 仍需开发的薄集成层

~~~text
现成目录树 ─┐
现成编辑器 ─┼─ 笔记界面适配 ─ 窄 IPC ─ VaultService ─ 用户的 .md 文件
现成搜索   ─┘                             │
                                   AI 的读/建/改工具
~~~

VaultService 首版只承担：

1. 打开、列出、创建、读取和保存知识库内文件。
2. 路径范围校验、同目录临时写入、备份和版本冲突检测。
3. 接收 chokidar 事件并更新界面/小规模搜索数据。
4. 将用户插入的课程图片复制到正式附件目录。
5. 向 AI 提供带范围和操作ID的文件工具。

这些是文件权限、数据保留和应用行为的接合点。现成编辑器和目录树并不自动提供它们。首版保留防止覆盖外部编辑的检查，复杂三方合并留到以后。

## 4. 首版做什么、后续做什么

| 首版保留 | 后续按实际需要增加 |
| --- | --- |
| B站与本地视频，只读进度、低清帧、字幕和已有独立回填 | 更多网站、完整已观看区间统计 |
| 发问时冻结来源，避免切视频后回答错课程 | 跨课程知识网络、完整图检索 |
| 打开已有Markdown目录，编辑/预览、文件树、基础搜索 | 完整wikilink解析、反向链接、知识图谱 |
| PDF当前页/选区问答 | 扫描PDF自动OCR、整本书深度索引 |
| 一个实际模型连接、视觉问答、AI保存/修改笔记 | 多模型高级路由、完整本地ASR/OCR管线 |
| 备份、冲突检测、附件持久化、重启保留课程归档 | 公开发行签名、自动升级、大规模性能优化 |

视频部分沿用现有 .mjs、文件归档和媒体回填，用适配层修必要缺口，不在首版全面改写 TemporalIndex 和持久化。先通过显式 source/visit/generation 和请求锚点隔离数据，修图像特征链；数据库化按数据量和查询需要渐进实施。

应用内部仍使用受控 IPC；沿用源码不等于照搬插件默认的开放 HTTP 桥接、C盘临时路径或重启清理行为。新应用使用独立D盘数据根，明确关闭重启清理；不改动原插件的运行目录。

## 5. 精简排期

以下为一名熟悉相关栈的开发者、依赖可获取且早期技术验证通过时的估算，不是日历日期承诺。

| 阶段 | 工作内容 | 工作量 |
| --- | --- | --- |
| M0 | 最小Electron验证：B站播放/读帧、本地解码、编辑器样例、模型连通 | 0.5–1 人日 |
| M1 | 分栏宿主、浏览器、本地视频、PDF.js基本阅读 | 1–2 人日 |
| M2 | 集成编辑器/目录树/监听/搜索，接文件服务与附件 | 1–2 人日 |
| M3 | 观察模块适配、必要特征修复、来源隔离、归档恢复 | 1.5–2.5 人日 |
| M4 | AI对话、冻结上下文、证据引用、笔记读写工具 | 1.5–2.5 人日 |
| M5 | 真实使用回归、冲突/取消/重启检查、可运行内部包 | 0.5–1 人日 |

基础合计 6–11 人日，预留约1人日集成余量，首个可用版本以 **7–12 人日** 为目标。单独笔记集成约 **1–2 人日**，不再按自建编辑器与完整笔记引擎估算。

如果真实 B站嵌入播放/取帧不通过，或已有知识库使用大量特殊语法，及时据验证结果重估，不能只为维持短排期隐藏问题。完整ASR和公开发行工作在实际首版基础上另排，不沿用旧的首版累计人日。

## 6. 精简不能省略的验收

- 用户继续看课时，AI读取过去证据不seek前台。
- 发问后切视频，回答和回填仍归原来源。
- AI保存普通Markdown后，用户能在本应用和Obsidian中继续编辑。
- Obsidian同时修改时，应用检测冲突并保留内容。
- 清视频缓存不删除笔记附件；重启不清所保留课程。
- 所有本轮新增应用临时路径在D盘。

这里没有减少用户确认的五类来源/能力；将高级知识管理和完整音频增强从首次交付拆开，并用现成组件减少重复开发。
